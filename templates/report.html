1. Abstract & Executive Summary

Modern municipal parking infrastructure depends heavily on automated license plate readers (ALPR) and ultrasonic bay sensors. Centralized architectures present critical privacy and security vulnerabilities: unencrypted license plates allow driver profiling, roadside payment kiosks are vulnerable to PIN brute-forcing, and rogue hardware can execute Denial-of-Service (DoS) frame flooding against barrier gates.

This project presents the Smart-Parking Edge Box Simulation: an autonomous on-site edge computing system that ingests encrypted sensor data, computes privacy-preserving metrics, grants temporary inspector delegations, and mitigates cyber attacks without exposing private driver telemetry.

Core Achievements & Highlights
  • Tamper-Proof Ingest: AES-256-GCM combined with ECDSA P-256 digital signatures to prevent sensor spoofing.
  • Driver Privacy Shield: Immediate license plate SHA-256 hashing and visual blurring, GPS truncation, and device ID rotation.
  • Honey Encryption Decoy Trap: Synthesizes believable dummy credit card numbers when wrong PINs are entered, catching attackers without alerting them.
  • Privacy Multi-Party Computation: Paillier Homomorphic Encryption (HE) and Functional Encryption (FE) to compute city-wide parking totals and EV grid loads without decrypting raw data.
  • Visual Real-World Simulator: A high-fidelity interactive dashboard simulating gates, cars, overhead sensors, and payment kiosks in real time.

2. System Architecture & Components

The system follows a modular edge-centric architecture containing four primary simulated subsystems alongside an edge box server:

Component Source File Role & Cryptographic Functionality
Camera Process camera.py Simulates optical gate cameras. Captures plate frames, blurs license plates, computes SHA-256 digests, signs ciphertexts with ECDSA (P-256), and encrypts payloads with AES-256-GCM and IBE.
Sensor Process sensor.py Simulates IoT ultrasonic bay sensors. Generates per-bay occupancy vectors (standard vs. EV bays), reduces GPS precision, rotates temporary hardware IDs, and authenticates readings via HMAC.
Parking Edge Server parking_edge.py Acts as the on-site security brain. Ingests encrypted telemetry, manages attribute-based policies, issues Proxy Re-Encryption keys, generates SSE trapdoors, and enforces rate limits.
Crypto Engine crypto_utils.py Houses modular implementations of all 11 cryptographic algorithms (AES-GCM, IBE, ABE, PRE, FE, Honey, SSE, Paillier HE, JWT, Rate Limiter).
Web Dashboard app.py & templates/index.html Flask REST API with a visual 2D parking lot simulator, automated gates, interactive PIN kiosk, and academic test harness.

3. Detailed Cryptographic Specifications

Step 1: AES-256-GCM + HMAC-SHA256 + ECDSA Ingest

Every camera and sensor encrypts outgoing packets with AES-256 in Galois/Counter Mode (GCM). Sensors sign the resulting ciphertext using Elliptic Curve Digital Signatures (ECDSA P-256). The edge box verifies the cryptographic signature before storing ciphertext, preventing man-in-the-middle tampering.

Step 2: Identity-Based Encryption (IBE)

Cameras encrypt readings directly using the string identifier of the parking facility (e.g., "LOT-3") as the public key. This removes the administrative overhead of exchanging public key certificates (PKI) between mobile edge nodes and roadside sensors.

Step 3: Attribute-Based Encryption (ABE)

Sensitive operational records are encrypted under a ciphertext-policy attribute-based scheme:

Policy: "ParkingAttendant AND Lot3" Authorized User Attributes: {"ParkingAttendant", "Lot3", "Shift-A"} --> Decryption: SUCCESS Unauthorized User Attributes: {"SecurityGuard", "Lot3"} --> Decryption: DENIED (PermissionError)

Step 4: Proxy Re-Encryption (PRE)

When municipal auditors or city inspectors conduct routine parking capacity checks, the parking operator does not reveal their master private keys. Instead, the edge box generates a re-encryption key rk_A->B that transforms operator ciphertexts into inspector ciphertexts without decrypting data in plaintext.

Step 5: Functional Encryption (FE)

The city power authority requires real-time knowledge of Electric Vehicle (EV) power grid load without tracking which specific bays are occupied. Functional Encryption evaluates an inner product over the binary occupancy vector:

FE Occupancy % = <occupancy_vector, weights> / total_bays FE Free EV Bays = <ev_vector, ev_filter_weights> (Returns exact EV count with zero identity leakage)

Step 6: Honey Encryption (PIN Protection & Decoy Trap)

Traditional PIN verification returns "Access Denied" upon failure, allowing attackers to incrementally search PIN spaces. Honey Encryption encrypts the credit card number under a 4-digit PIN mapped to a distribution-transforming encoder (DTE):

  • Correct PIN (4829): Decrypts the driver's genuine card (4532-1234-5678-9012).
  • Incorrect PIN (e.g., 1234): Generates a syntactically valid, plausible dummy credit card number (e.g., 4916-8321-4491-0023) via a pseudo-random permutation. The adversary is lured into a honeypot while genuine data remains secure.

Step 7: Searchable Symmetric Encryption (SSE)

Encrypted parking events are indexed using blind cryptographic hashes. An operator submits a search trapdoor: T_w = HMAC(K_search, keyword). The edge box searches over the encrypted index and returns matching records without learning what keyword was searched.

Step 8: Paillier Homomorphic Encryption (HE)

To compute city-wide parking availability across multiple edge boxes, edge nodes encrypt their local free spot counts using the Paillier cryptosystem. A centralized city coordinator multiplies the ciphertexts together:

Enc(m1) * Enc(m2) * Enc(m3) = Enc(m1 + m2 + m3) mod n^2

The city learns the total available parking spots in the district without any edge box revealing individual occupancy details.

Step 9: JSON Web Tokens (JWT) Multi-Domain Auth

The edge server issues compact, cryptographically signed HS256 tokens:

  • Operator Token: Single-domain credentials for administrative tasks (expires in 8 hours).
  • City Payment Token: Claims for automated tolling and municipal transit wallets.
  • Ticket Handover Token: Transferred securely to driver mobile apps for contact-free exit payment.

Step 10: Privacy Protections & Anonymization

  1. License Plate Hashing: Raw plates are converted to irreversible SHA-256 digests (KA01AB1234 → 9f86d08...).
  2. Visual Plate Blurring: Replaces middle characters with masks (KA01**1234) for human displays.
  3. Location Coordinate Truncation: Truncates GPS decimals to 2 places (~1.1 km precision) to obscure exact vehicle parking slots.
  4. Device ID Rotation: Rotates temporary hardware UUIDs every 10 frames to defeat hardware fingerprinting.

Step 11: Token-Bucket Rate Limiter & Flood Quarantine

External cameras are susceptible to firmware compromise. The edge server maintains a token-bucket limiter (Capacity = 10 tokens, Refill = 2 tokens/sec). When an attacker floods the edge box with 20 frames/sec, the bucket is depleted and triggers an immediate hardware quarantine in < 50 milliseconds.

6. Conclusion

The Smart-Parking Edge Box Simulation proves that zero-trust cryptography can be effectively deployed on edge hardware. By shifting data encryption, privacy anonymization, and threat mitigation to the parking edge, municipal operators protect citizen privacy, thwart brute-force and DoS attacks, and securely share data with city authorities without centralized cloud vulnerabilities.
