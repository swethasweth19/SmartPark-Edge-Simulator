1. Abstract & Executive Summary

Modern smart parking infrastructure relies heavily on cloud-connected automated license plate readers (ALPR) and ultrasonic bay occupancy sensors. However, traditional centralized architectures present severe privacy and cyber-security vulnerabilities: cleartext license plates allow continuous driver profiling and location tracking, payment terminals are vulnerable to PIN brute-force attacks, and rogue hardware can execute Denial-of-Service (DoS) frame flooding against barrier gates.

This project designs, implements, and evaluates the Smart-Parking Edge Box Simulation: an autonomous edge server positioned directly at municipal parking facilities. The edge box validates and stores encrypted data locally, calculates privacy-preserving aggregates, provides safe cross-domain delegations, and actively defends against cyber threats without exposing private driver telemetry.

Key Innovation Highlights
  • Zero-Trust Ingestion: Per-sensor AES-256-GCM encryption paired with ECDSA P-256 digital signatures to prevent sensor spoofing.
  • Driver Privacy Shield: Immediate license plate SHA-256 hashing and visual blurring, GPS coordinate reduction, and ephemeral device ID rotations.
  • Active Honey Encryption Decoy Trap: Synthesizes believable dummy credit card numbers when incorrect PINs are entered, baiting intruders without alerting them.
  • Safe Multi-Party Computation: Paillier Homomorphic Encryption (HE) and Functional Encryption (FE) to compute city-wide parking totals and EV grid loads without decrypting raw data.
  • Visual Real-World Simulator: A high-fidelity interactive dashboard simulating gates, cars, overhead sensors, and payment kiosks in real time.

The system follows an edge-centric microservice architecture containing three primary simulated processes alongside an edge box server and a real-time web visualization layer:

3. Detailed Cryptographic Specifications

Step 1: AES-256-GCM + HMAC-SHA256 + ECDSA Ingest

Every camera and sensor encrypts outgoing packets with AES-256 in Galois/Counter Mode (GCM), providing authenticated encryption with associated data (AEAD). Sensors sign the resulting ciphertext using Elliptic Curve Digital Signatures (ECDSA P-256). The edge box verifies the cryptographic signature against the sensor's public key before storing ciphertext, preventing man-in-the-middle tampering.

Step 2: Identity-Based Encryption (IBE)

Cameras encrypt readings directly using the string identifier of the parking facility (e.g., "LOT-3") as the public key. This removes the administrative overhead of exchanging public key certificates (PKI) between mobile edge nodes and roadside sensors.

Step 3: Attribute-Based Encryption (ABE)

Sensitive operational records (revenue tallies, zone alerts) are encrypted under a ciphertext-policy attribute-based scheme:

Policy: "ParkingAttendant AND Lot3" Authorized User Attributes: {"ParkingAttendant", "Lot3", "Shift-A"} --> Decryption: SUCCESS Unauthorized User Attributes: {"SecurityGuard", "Lot3"} --> Decryption: DENIED (PermissionError)

Step 4: Proxy Re-Encryption (PRE)

When municipal auditors or city inspectors conduct routine parking capacity checks, the parking operator does not reveal their master private keys. Instead, the edge box generates a re-encryption key rk_A->B that transforms operator ciphertexts into inspector ciphertexts without ever decrypting the data in plaintext.

Step 5: Functional Encryption (FE)

The city power authority requires real-time knowledge of Electric Vehicle (EV) power grid load without tracking which specific bays are occupied. Functional Encryption evaluates an inner product over the binary occupancy vector:

FE Occupancy % = / total_bays FE Free EV Bays = (Returns exact EV count with zero identity leakage)

Step 6: Honey Encryption (PIN Protection & Decoy Trap)

Traditional password/PIN verification returns "Access Denied" upon failure, allowing attackers to incrementally search PIN spaces. Honey Encryption encrypts the credit card number under a 4-digit PIN mapped to a distribution-transforming encoder (DTE).

  • Correct PIN (4829): Decrypts the driver's genuine card (4532-1234-5678-9012).
  • Incorrect PIN (e.g., 1234): Generates a syntactically valid, plausible dummy credit card number (e.g., 4916-8321-4491-0023) via a pseudo-random permutation. The adversary is lured into a honeypot while genuine data remains secure.

Step 7: Searchable Symmetric Encryption (SSE)

Encrypted parking events are indexed using blind cryptographic hashes. An operator submits a search trapdoor: T_w = HMAC(K_search, keyword). The edge box searches over the encrypted index and returns matching records without learning what keyword was searched.

Step 8: Paillier Homomorphic Encryption (HE)

To compute city-wide parking availability across multiple edge boxes, the edge nodes encrypt their local free spot counts using the Paillier cryptosystem. A centralized city coordinator multiplies the ciphertexts together:

Enc(m1) * Enc(m2) * Enc(m3) = Enc(m1 + m2 + m3) mod n^2

The city learns the total available parking spots in the district without any edge box revealing individual occupancy details.

Step 9: JSON Web Tokens (JWT) Multi-Domain Auth

The edge server issues compact, cryptographically signed HS256 tokens:

  • Operator Token: Single-domain credentials for administrative tasks (expires in 8 hours).
  • City Payment Token: Claims for automated tolling and municipal transit wallets.
  • Ticket Handover Token: Transferred securely to driver mobile apps for contact-free exit payment.

Step 10: Privacy Protections & Anonymization

The edge box enforces privacy-by-design through four distinct safeguards:

  1. License Plate Hashing: Raw plates are converted to irreversible SHA-256 digests (KA01AB1234 → 9f86d08...).
  2. Visual Plate Blurring: Replaces middle characters with masks (KA01**1234) for human displays.
  3. Location Coordinate Truncation: Truncates GPS decimals to 2 places (~1.1 km precision) to obscure exact vehicle parking slots.
  4. Device ID Rotation: Rotates temporary hardware UUIDs every 10 frames to defeat hardware fingerprinting.

Step 11: Token-Bucket Rate Limiter & Flood Quarantine

External cameras are susceptible to firmware compromise. The edge server maintains a token-bucket limiter (Capacity = 10 tokens, Refill = 2 tokens/sec). When an attacker floods the edge box with 20 frames/sec:

  • The first 10 frames consume available burst tokens.
  • Subsequent frames deplete the bucket and immediately trigger a hardware quarantine.
  • The rogue camera is isolated in < 50 milliseconds, preventing barrier gate denial-of-service.

6. Conclusion

The Smart-Parking Edge Box Simulation demonstrates that advanced zero-trust cryptography can be effectively deployed on resource-constrained edge hardware. By shifting data encryption, privacy anonymization, and threat mitigation to the parking edge, municipal operators can protect citizen privacy, thwart brute-force and DoS attacks, and securely share data with city authorities without centralized cloud vulnerabilities.
